## 1. D2 — 픽셀 배율 · 공간 비례 · 지리 압축을 분리

### 1-1. 픽셀 배율 (화면 렌더 계약)
R1의 "1.5배를 1배 렌더 + CSS 2배로 정수 유지"는 결과가 2배라 성립하지 않음 — **철회**.

정수 배율은 CSS px가 아니라 **장치 픽셀(device px) 기준**으로 정의한다.

| 기호 | 정의 |
|---|---|
| `DPR` | `window.devicePixelRatio` |
| `devW, devH` | `innerWidth·DPR`, `innerHeight·DPR` (장치 픽셀) |
| `k` | 게임 픽셀 1개당 장치 픽셀 수, **정수 ≥ 1** |
| 내부 렌더 크기 | `VW = ceil(devW / k)`, `VH = ceil(devH / k)` (게임 픽셀) |
| CSS 크기 | `VW·k / DPR` × `VH·k / DPR` (뷰포트보다 최대 k/DPR px 클 수 있음 → `overflow:hidden`으로 잘림, **늘이지 않음**) |
| `image-rendering` | `pixelated` — 게임 픽셀 1개 = 정확히 k×k 장치 픽셀 |

`k` 선택 규칙:
- **좁은 화면**(`innerWidth < 600` CSS px): `k = max(1, round(DPR))` → CSS 기준 **1배**. 390×844 @DPR3 → k=3, 시야 390×844 게임 px(= 12.2×26.4 타일).
- **그 외**: `k = max(1, floor(min(devW / 640, devH / 400)))` → 1440×900 @DPR1 → k=2(CSS 기준 **2배**), 시야 720×450 게임 px(= 22.5×14.1 타일). @DPR1.25(이 노트북 가능성) → devW 1800 → k=2, 시야 900×563(장치 픽셀 정수 대응 유지, 시야만 넓어짐).
- 1920×1080 @DPR1 → k=2, 시야 960×540.

포인터 좌표 변환(클릭 이동·디버그):
```
rect = canvas.getBoundingClientRect()
gameX = cam.x + (clientX - rect.left) · DPR / k
gameY = cam.y + (clientY - rect.top)  · DPR / k
```
DOM 라벨·태그 위치: `cssX = (worldX - cam.x) · k / DPR`.
리사이즈·DPR 변경(`matchMedia('(resolution: …)')`) 시 재계산.

확인 대상(G1·G5에서 실제 화면 캡처): 1440×900 DPR1 / 1440×900 DPR1.25 / 390×844 DPR3 각각의 시야, HUD 겹침, 조이스틱 반경·액션 버튼 위치.

### 1-2. 공간 비례 (사람이 걷는 크기)
32px 한 칸을 "12~15m"로 해석하던 R1 서술 **철회**. 한 칸은 지리 거리 단위가 아니라 **사람 기준 공간 단위**다.

| 요소 | 크기(타일) | 화면(k=2 기준 CSS px) |
|---|---|---|
| 캐릭터 | 폭 0.75 × 높이 1.25 (24×40 px), 충돌 히트박스 14×6 px(발밑) | 48×80 |
| 문 | 폭 1~2, 높이 1.5 | 64~128 × 96 |
| 건물 층고 | 2.5 / 층 | 160 / 층 |
| 보도 | 2 (간선) / 1 (이면) | 128 / 64 |
| 차로 1개 | 2 | 128 |
| 간선(중앙대로·충장대로) | 차도 8(4차로로 표현) + 보도 2×2 = **12** | — |
| 보조간선(대청로·태종로) | 차도 4 + 보도 2×2 = **8** | — |
| 이면도로 | 보차혼용 **4** | — |
| 골목·계단 | **2** | — |
| 안벽 가장자리 | 보행 1 + 볼라드 열 | — |

### 1-3. 지리 압축 (랜드마크 사이 거리)
- 지리 투영: 등거리 원통(equirectangular), 기준 위도 35.105°, `x = (lon − lon0)·cos(35.105°)·111,320m / g`, `y = (lat0 − lat)·110,950m / g`.
- **g = 10 m / 타일** (지리 압축 축척). 공간 비례(1-2)와 별개.
- 중앙동 구역 포함 범위: **위도 35.0925–35.1185, 경도 129.0280–129.0480**
  → 남북 2.89km = **289 타일**, 동서 1.82km = **182 타일** → **맵 184 × 292 타일**(여백 포함).
  - R1의 "160×120 × 12~15m = 1.44~1.8km"는 부산역↔영도대교 2.2km를 못 담음 → **맵 크기를 키우는 쪽으로 결정**(포함 범위는 유지, 지리 압축은 10m로 고정).
- 결과: 부산역 → 출입국청 직선 약 1.2km = 약 120 타일 → 걷기 4.5 타일/s로 약 27초, 달리기 약 13초.
- 왜곡의 출처를 명시: 사람 비례의 도로 폭(간선 12타일 = 지리 120m, 실제 40m 안팎)을 지리 10m/타일 위에 그리므로 **도로는 실제보다 넓고 블록 안 건물은 실제보다 적다**. 그래서 OSM에서 **간선·보조간선·주요 이면도로만** 가져오고, 블록 내부 골목은 저작한다. 랜드마크·교량 끝점·해안선은 투영 좌표를 고정점으로 지킨다.
- 렌더: 184×292×32px = 5,888×9,344 px 단일 캔버스는 메모리 과다(≈220MB) → **청크 렌더**(16×16 타일 = 512px 청크, 화면 주변만 생성, LRU 64개).

## 2. 렌더 계약 — 앞뒤 관계 규칙 (R1 49행 vs 135행 충돌 해소)

R1의 "지붕·수관을 항상 마지막 오버헤드 레이어에 그림"은 앞에 선 캐릭터까지 덮으므로 **철회**.

### 2-1. 규칙
1. 모든 그리기 단위는 **`sortY` = 지면 접지선(발자국 남쪽 끝) y**를 가진다. 캐릭터는 발끝 y.
2. 건물·나무는 **본체 + 지붕/수관을 한 스프라이트**로 묶어 같은 `sortY`로 그린다(지붕을 따로 떼지 않음).
3. `sortY` 오름차순 그리기. 같으면 x 오름차순, 다음 고유 id(안정 정렬).
4. **스프라이트는 발자국 좌우 폭을 넘지 않는다**(처마는 발자국 안쪽으로). → 캐릭터가 건물 동·서 옆면에 있을 때는 픽셀이 겹치지 않으므로 정렬 순서와 무관.
5. 발자국이 직사각형이 아닌 건물(L자 등)은 **직사각형 조각으로 분할**, 조각마다 `sortY`.
6. 충돌 발자국 깊이 ≥ 캐릭터 히트박스 깊이 → 캐릭터 발끝이 건물 접지선과 같은 y에 놓일 수 없음(앞뒤 판정이 애매한 위치가 생기지 않음).
7. **오버헤드 레이어**(항상 위)는 "모든 보행 지점에서 캐릭터 머리보다 높은 것"만: 구름 그림자(디더), 날아가는 갈매기, 보행 가능 지면 위를 지나는 고가 상판(중앙동 구역엔 없음). 지붕·수관·간판은 금지.

### 2-2. 검증 장면 (G7에서 자동 판정)
대상: 출입국청 본관(대형), 상가 1동(중형), 나무 1그루, 영도대교 난간.

| 위치 | 기대 |
|---|---|
| 정면(남쪽, 문 앞) | 캐릭터 전부 보임 |
| 뒤(북쪽, 지붕 뒤) | 캐릭터의 지붕과 겹치는 부분이 가려짐 |
| 동쪽 옆 / 서쪽 옆 | 캐릭터 전부 보임, 건물도 안 깎임 |
| 북동·북서 모서리 | 뒤로 판정 → 겹친 부분 가려짐 |
| 남동·남서 모서리 | 앞으로 판정 → 전부 보임 |
| 나무 북쪽 / 남쪽 | 수관에 가려짐 / 전부 보임 |

## 3. D4 — OSM 유래 데이터의 배포 방식

### 3-1. 근거
- OSMF Produced Work 지침: 결과물이 원본 데이터 추출용이 아니면 Produced Work(이미지·게임 화면 등). Produced Work를 공개하면 바탕 DB 또는 그 변경분을 공개해야 함(ODbL 4.6) — https://osmfoundation.org/wiki/Licence/Community_Guidelines/Produced_Work_-_Guideline
- OSMF Licence and Legal FAQ: OSM 데이터를 수정·보강·확장하면 Derivative Database. 요청 시 "데이터 + Derivative Database를 ODbL로" 또는 "Derivative Database를 만드는 수단"을 제공. 독립 DB의 모음(Collective Database)이면 다른 부분엔 share-alike 미적용. 디지털 화면 표기는 openstreetmap.org/copyright 링크, 보통 우하단 — https://osmfoundation.org/wiki/Licence/Licence_and_Legal_FAQ
- ODbL 1.0 원문 — https://opendatacommons.org/licenses/odbl/1-0/
- 게임 화면(GitHub Pages로 누구나 접속)은 **공개 사용(Publicly Use)** 에 해당 → 4.6 의무 발생으로 본다. 대시보드 레포가 비공개여도 Pages는 공개.

### 3-4. D5 구현 규칙 (배경 교량)
- 배경 교량은 **장식 레이어 오브젝트**로만 존재. 그 아래 지면 타일은 수역 그대로(차단). 교량 상판은 지면 타일로 만들지 않는다 → `blocked()`가 그대로 막음.
- 보행 교량(영도대교·부산대교)은 지면 레이어의 `BRIDGE_WALK` 타일 + 난간 충돌 rect.
- 중앙동 구역 범위(경도 ≤ 129.048)에는 부산항대교(129.064)가 들어오지 않음. 원경 표현이 필요하면 맵 밖 배경 그림으로만.

## 4. D6 — 게이트 재정의 (통과 기준을 사전 고정)

모든 자동 게이트는 `tools/gates/run-all.mjs` 하나로 실행하고, **각 게이트가 필수 필드·오류 수·완료 플래그를 직접 검사해 실패 시 종료 코드 ≠ 0**. JSON 출력만으로 성공 처리하지 않는다. 각 게이트에는 **일부러 실패시키는 변형(negative control)** 을 같이 돌려, 검사기가 실제로 FAIL을 낼 수 있음을 함께 증명한다.

| 게이트 | 방법 | 통과 기준 | negative control |
|---|---|---|---|
